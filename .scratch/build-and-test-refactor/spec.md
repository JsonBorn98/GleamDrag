# Spec: 构建与验证重构（Candidate 01 + 工程壳迁移）

依据：架构评审 2026-09-16 Candidate 01 与技术选型推荐；ADR 0001（WXT+Vite+Bun）、ADR 0002（测试双栈）；术语表：纯逻辑测试、扩展内契约测试。

## 问题陈述

作为这个个人维护扩展的唯一开发者，我现在无法信任自己的验证结果：跑测试时即使有用例失败，命令也返回退出码 0（退出码判定读错字段），CI 从来不跑测试只构建上传，后台执行器的关键测试被注释掉无人发现。同时构建链路把 Windows 差异、GNU shell 依赖、包管理器细节全部暴露给我——我的开发机上甚至没有 make 和构建脚本硬编码的 Firefox 变体，验证链路在本机根本跑不通。每次改动后我得不到可靠的绿色或红色信号，后续任何后台、拖拽、配置重构都缺少保护网。

## 方案

先修验证闭环让它可信（退出码契约 + 恢复被遗漏的测试 + 本机可跑的真实浏览器基线），再用 WXT + Vite 重构构建编排、一次性切换 Bun，产出 Firefox 与 Chromium 双 MV3 产物；Svelte 升 5 只做最小兼容；测试拆成双栈——纯逻辑测试迁 Vitest 离线秒级反馈，扩展内契约测试留在真实扩展页面跑；CI 与本地跑同一条命令，每次构建+类型+双套测试；双产物验证通过后删除旧构建脚本，不并存两套。

## 用户故事

1. 作为唯一维护者，我想要测试有用例失败时命令返回非零退出码，以便本地脚本和 CI 都能可靠地红绿。
2. 作为唯一维护者，我想要一个故意失败的 fixture 套件使本地与 CI 都返回非零，以便退出码契约本身被持续验证、不会悄悄回归。
3. 作为唯一维护者，我想要恢复被注释掉的后台执行器契约测试，以便动作执行从一开始就在保护范围内。
4. 作为唯一维护者，我想要在本机 Windows 上跑通现有验证链路（进程启动、Firefox 路径、不依赖 make），以便迁移前拿到真实浏览器内的绿色基线。
5. 作为唯一维护者，我想要包管理器一次性从 pnpm 切到 Bun（lockfile、CI、仓库指南同批改齐），以便不存在「本地一套命令、CI 另一套」的不一致。
6. 作为唯一维护者，我想要用一条命令构建出 Firefox 与 Chromium 两份 MV3 产物 zip，以便两个浏览器共享同一构建入口。
7. 作为唯一维护者，我想要 Firefox 产物显式声明 Manifest V3，以便不落回 WXT 对 Firefox 默认 MV2 的行为。
8. 作为唯一维护者，我想要 Svelte 5 最小兼容迁移（保留现有组件写法，只修挂载 API 与 custom element 编译不兼容点），以便能用官方 Svelte 模块而拖拽与设置页行为不变。
9. 作为唯一维护者，我想要 TypeScript strict 开启且类型检查全绿，以便类型反馈与测试反馈一样可信。
10. 作为唯一维护者，我想要纯逻辑测试在 Vitest 里离线跑，以便秒级反馈、不需要起浏览器。
11. 作为唯一维护者，我想要扩展内契约测试（含执行器）在真实扩展页面里跑并通过 WebSocket 上报，以便依赖扩展运行时的行为被真环境验证而不是被 mock 糊弄。
12. 作为唯一维护者，我想要 Playwright 以 Chromium persistent context 自动加载产物并跑扩展内套件，以便 Chromium 侧有可重复的自动化验收。
13. 作为唯一维护者，我想要 web-ext 自动起本机 Firefox 跑同一套扩展内契约测试，以便 Firefox 侧与 Chromium 侧用同一验收路径。
14. 作为唯一维护者，我想要 CI 每次推送都跑构建、类型检查、Vitest、扩展内套件并上传双产物 zip，以便远端与本地看到同一份可信反馈。
15. 作为唯一维护者，我想要 CI 的 GitHub Actions 与 Node 升到受支持版本，以便不再依赖已退役的 action 版本。
16. 作为唯一维护者，我想要双 MV3 产物验证通过后删除旧构建脚本（Makefile 与手写构建编排），以便仓库里不长期并存两套构建。
17. 作为未来的 agent 会话，我想要仓库指南里的命令与实际工具链一致（Bun、WXT、Vitest），以便不按过期文档操作。
18. 作为唯一维护者，我想要明确的 Chrome/Edge stable 手动装包验收路径，以便真实浏览器验收不被 Playwright 自带 Chromium 冒充。
19. 作为唯一维护者，我想要每个里程碑一个 Conventional Commit，以便中途任一步可回滚、可审查。

## 实现决策

- 构建编排交给 WXT（内置 Vite）：接管 entrypoint、产物生成、开发重载；manifest 中浏览器差异（Firefox 专属权限、Chromium service_worker、测试目标 CSP 覆盖）在 WXT manifest 配置里等价保留，不引入第二个手写 manifest 生成器。依据 ADR 0001。
- 版本组合在迁移实施时按选定 release 的 peerDependencies 重新验证后锁定（调研值：WXT 0.21.4 / Svelte 5.57.0 / Vite 8.3.0，非锁定值）。
- 包管理器一次性切 Bun：删 pnpm lockfile、生成 bun lockfile、CI 与仓库指南同批更新；依据 ADR 0001 与全局工具链偏好。
- Svelte 5 走最小兼容：组件保持现有写法（legacy 模式），只修挂载/卸载 API 与 custom element 编译不兼容点；不迁 runes、不改拖拽与设置页逻辑。
- TypeScript strict 跟随 WXT 生成配置开启，迁移中修到类型检查全绿，个别错误多的文件做局部最小修正、不改运行时行为。
- 测试双栈依据 ADR 0002：不依赖浏览器扩展 API 的纯逻辑测试（工具、日期、变量替换、本地化、解析器、菜单构建等）迁 Vitest；依赖扩展运行时的留在扩展内契约测试，经扩展测试页 + WebSocket 上报，退出码契约由故意失败 fixture 验证。
- 扩展测试页只在测试构建中打包（普通产物不含测试入口），沿用测试目标 CSP 覆盖仅限 Firefox 测试构建。
- 恢复执行器测试时只修两处不改变动作语义的小 bug：script 分支落入 default 分支、缺脚本时读取 script.id 的错误；动作语义级修复留给后台重构。
- 旧链路的 Windows 过渡修复（进程启动扩展名、Firefox 可执行路径、绕开 make）只服务迁移前基线，随旧脚本一起删除，不带入新链路。
- 旧构建资产（Makefile 与全部手写构建/manifest 脚本）在双 MV3 产物经真浏览器验证后同批删除。
- CI：安装依赖 → 类型检查 → Vitest → WXT 双产物构建 → zip 上传 → Firefox 扩展内契约套件；actions 升 v4、Node 24；Playwright Chromium 验收在本地/按需跑，不冒充三浏览器验收。
- 提交节奏：分阶段 Conventional Commits（fix 退出码 → 恢复测试 → 本机基线 → Bun 切换 → WXT 迁移 → Svelte 5 → Vitest → CI → 删除旧脚本 → 文档），默认只本地提交。

## 测试决策

- 好测试 = 只在主 seam（统一命令入口）上观察外部行为：退出码、产物 zip 可加载、扩展测试页上报的结果；不测构建内部实现细节。
- 退出码契约测试：对故意失败的 fixture 套件断言非零退出——这是本 spec 最重要的新先例，防假绿回归。
- 纯逻辑测试沿用现有 colocated `*.test.ts` 风格与 Chai 断言习惯，迁 Vitest 后断言库换 expect 但行为断言保持外部行为导向。
- 扩展内契约测试先例：现有浏览器内 Mocha 套件（经 WebSocket 上报）；执行器测试恢复后归入此栈。
- 迁移期顺序保障：旧链路先拿真实浏览器绿色基线，WXT 迁移后同套件再绿一次，两次绿之间才删旧链路——这是「不把假绿当正确性证据」的直接应用。
- CI 与本地跑同一条命令；故意失败必须使本地和 CI 都失败（验收标准的一部分）。

## 范围外

- 后台操作重构（评审 02）：执行完成语义、会话状态、按 key 广播——仅两处不动语义的小 bug 修复除外。
- 拖拽会话重组（评审 03）：缓存、rAF 绘制合并、性能 trace 基线。
- 配置版本化 schema 与校验库引入（评审 04）：Zod/Valibot 选型、导入校验、迁移 fixture。
- 浏览器能力 adapter（评审 05）：图片字节复制、用户脚本 world/权限、Firefox 容器。
- Svelte runes 全量迁移与设置页 UI 改版。
- Firefox 签名与任何外部上传发布动作（需另行授权）。
- 向上游开 PR 或对外发布；push 到远程需另行明确要求。

## 补充说明

- 迁移约束（来自评审与外部参考核对）：WXT 当前对 Firefox 默认 MV2，必须显式选 MV3；官方 Svelte 模块要求 Svelte≥5，不存在「保留 Svelte 3 runtime 直插」；Bun 迁移需 lockfile/CI/指南一次改齐。
- Playwright 扩展路径仅支持 Chromium persistent context；Chrome/Edge stable 手动 unpacked 装包验收是发布可用性验收的独立步骤，由维护者本人执行。
- 本 spec 对应的报告 Sequence 为步骤 1（验证闭环）+ 步骤 2（工程壳）；步骤 3-5（后台、配置、拖拽、高级能力）在后续 spec。
